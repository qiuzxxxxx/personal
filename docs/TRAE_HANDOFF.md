## 二、待评审产品决策：二维码改为跨设备登录令牌

### 目标

将当前“手机扫码上传”的二维码升级为短时跨设备授权：用户在已登录设备生成二维码，另一台设备扫码后，经确认以该账号的身份建立受限会话；从手机上传的资料自动进入该账号的私人资料库/指定文件夹，并在原设备同步显示。

### 当前决定

- **暂不实现，只记录方案。**
- 该改动会扩大认证边界，不能直接把现有上传票据改成长期登录 Token，也不能在二维码中放账号密码、DRF Token 或任何可重复使用的凭据。
- 默认建议优先实现“仅上传权限的设备会话”。如果确实需要完整登录，必须在界面上明确提示并由原设备或扫码设备再次确认。

### 推荐交互流程

1. 已登录用户点击“跨设备登录/手机上传”，后端创建一次性授权会话。
2. 页面展示二维码、剩余有效时间和待授权设备状态。
3. 二维码仅携带高熵随机挑战值或短链接，不携带长期凭据。
4. 手机打开授权页，显示账号、设备、时间和权限范围，并要求用户确认。
5. 后端原子消费挑战值，签发短期且权限受限的设备会话；同一挑战只能成功一次。
6. 手机上传的文件由后端根据已认证用户归属写入该账号的资料库，不接受前端传入任意用户 ID。
7. 原设备通过轮询或 WebSocket 得知授权、上传和同步结果；用户可随时撤销该设备会话。

### 后端建议设计

- 新建独立模型，例如 `DeviceAuthorizationSession`，不要复用当前上传会话的认证类。
- 建议字段：创建用户、随机挑战摘要、权限范围、过期时间、消费时间、撤销时间、设备摘要、IP 摘要和审计时间戳。
- 数据库只保存挑战值的哈希摘要；原始挑战值仅在创建时返回一次。
- 推荐接口：创建授权、查询状态、确认授权、消费授权、撤销设备、上传文件。
- 权限范围至少区分 `upload_only` 与 `full_login`。默认 `upload_only`。
- 上传归属完全从服务端认证上下文读取，并复用现有文件类型、1 GiB 大小限制、配额、存储和杀毒/内容检查策略。

### 强制安全要求

- 随机挑战至少 256 bit；有效期建议 2–5 分钟；一次性、原子消费、防重放。
- 全程 HTTPS；响应使用 `Cache-Control: no-store`；授权页使用严格 Referrer Policy。
- 长期 Token、密码和用户隐私数据不得进入二维码、URL 查询串、访问日志或前端持久化日志。
- 加入创建、确认、消费和失败次数的速率限制；防止枚举、暴力尝试与会话固定。
- 账号禁用、改密、主动退出全部设备时，应撤销相关设备授权和会话。
- 完整登录必须有显式确认；建议同时在原设备显示“设备/IP/时间/权限”，支持一键拒绝。
- 记录可审计事件，但审计日志不得记录原始挑战值或访问令牌。
- 不允许借二维码绕过账号权限：普通用户仍只能访问自己的资料；最高管理员权限不得被普通二维码继承或提升。

### 前端工作项

- 桌面端：二维码弹窗、倒计时、授权状态、拒绝/撤销、异常与过期提示。
- 移动端：授权确认页、权限说明、上传进度、资料归属提示、成功后安全退出。
- 账号安全页：已授权设备列表、最后活动时间、权限范围、单设备撤销和全部撤销。
- 禁止在 `localStorage` 长期保存一次性挑战值；完整登录会话沿用项目统一认证存储与退出逻辑。

### 测试与验收

- 正常扫码、过期、重复扫码、并发消费、撤销、账号禁用、改密后失效。
- A 用户二维码不能上传到 B 用户目录；篡改用户 ID、文件夹 ID、权限范围均应被拒绝。
- 未确认时不能签发会话；一次性挑战首次成功后再次使用必须失败。
- 上传完成后两端均显示同一账号资料，权限、文件大小、类型和时效限制保持一致。
- 日志、浏览器历史、二维码截图中不得出现可长期登录的凭据。
- 回滚时关闭功能开关并撤销未消费授权，不影响原有账号登录和普通文件上传。
